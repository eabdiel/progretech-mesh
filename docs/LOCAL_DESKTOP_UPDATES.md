# Local Mesh desktop and Git updates

The workstation edition uses the existing connected local Mesh service and role bridge. The Mesh Local desktop launcher opens `http://127.0.0.1:8080` in an app window and starts its user service when necessary. Owner data, enrollment, role settings and models remain in their established home directories.

The Fleet and Factory top menus show **Check for updates** only for the configured local installation. Checking fetches the host-owned `origin` remote's `releases/mesh-local` channel, reports the installed revision and available commit subjects, and leaves the installed checkout untouched. **Install update** is a separate owner action for that checked revision. The hosted edition does not expose an updater API.

Install metadata is under `~/.local/state/progretech-mesh/installation/`. The installation's `config.json` pins the existing repository, `origin`, release channel and release directory. Git credentials remain in the host's credential store. Menu requests cannot supply paths, commands, repositories or remotes. Both actions require the owner's local Mesh session and same-origin POST. Git hooks are disabled for updater Git commands.

Updates must descend from the installed revision. Local source edits, divergent history, unavailable upstream or active Mesh requests block cutover without discarding work. The worker creates a separate detached Git worktree and Python environment for the candidate, installs declared dependencies there, checks Python syntax, and waits up to three minutes for active Mesh requests to finish before switching. A continuing busy state leaves the running release in place and reports a deferred update. It atomically changes the installation record and restarts only the local Mesh web service. The prior worktree/interpreter are retained. A failed service health check restores that installation record and restarts the previous release; rollback health failures are reported honestly.

This update path updates the local web application. Workstation role runtimes, the shared factory bridge, gateway configuration, credentials and models are not reconfigured by it. Those independently deployed services retain their existing update/activation process. A future source release must include valid `mesh-release.json` metadata and be published as a fast-forward on `releases/mesh-local`; this channel deliberately avoids replacing the installed approved factory features with an unrelated checkout of main.

The stable server and app-window launcher sources are `install/mesh-local-server.py` and `install/mesh-local-launcher.py`. The workstation install copies them to `~/.local/bin/mesh-local-server` and `~/.local/bin/mesh-local`. Git application updates use the existing stable server entry point and installation record, so replacing application files does not overwrite the running interpreter or owner workspaces.
